## 3. 전처리 흐름

```
data/raw/*.csv
   │  01_raw.sql      CSV → 원본 테이블 (raw_s1 ~ raw_s4). 값은 고치지 않는다
   ▼
   │  02_mapping.sql  참조 테이블 (ref_industry, ref_area)
   ▼
   │  03_clean.sql    걸러내기 + filter_log 기록 → clean_s1 ~ clean_s4
   ▼
   │  04_views.sql    지표가 조회하는 뷰 4종
   ▼
v_store / v_industry_spend / v_area_spend / v_arrivals
   │  지표 서비스 3종 (JdbcClient SQL)
   ▼
에이전트 도구 결과 → LLM 문장 → 화면
```

`DataLoader`가 앱 시작 시 `data/sql/*.sql`을 파일 이름 순서로 실행한다.
모든 SQL이 `CREATE OR REPLACE`라 몇 번을 다시 실행해도 같은 결과가 나온다.
SQL 안의 `${DATA_DIR}`는 `app.data-dir`의 절대경로로 치환되므로 실행 위치에 영향을 받지 않는다.

### 3.1 문자열 정리

S1 원본은 CP949라 UTF-8로 변환했고, 값 끝에 공백이 붙은 경우가 있다.
예를 들어 상권업종중분류명이 `비알코올`이 아니라 `비알코올 `로 들어와 있어 그대로 비교하면 카페 업종 전체가 매핑에서 빠진다.
적재 시점에 `trim(nfc_normalize(...))`로 네 파일 모두 정리했다.

### 3.2 코드 체계 통합

데이터마다 지역 코드 체계가 다르다.

| 데이터 | 지역 키 | 처리 |
| --- | --- | --- |
| S1 | **행안부 행정동코드 8자리** (예: 노형동 `50110660`) | **기준 키로 채택** |
| S3 | 자체 읍면동코드 7자리 (예: 노형동 `3901066`) | 버리고 **읍면동명으로 조인** |

S1의 행정동명 43개와 S3의 읍면동명 43개가 **모두 일치**하는 것을 확인하고 이름으로 이었다 (2026-11-17 확인).
`ref_area(emd_code, emd_name, city, s3_name)`가 이 대응을 보관한다.
S1에 제주 전체 43개 행정동이 모두 존재하므로 행정표준코드 별도 내려받기는 필요하지 않았다.

### 3.3 외식업 7개 업종 매핑

| 코드 | 화면 이름 | S1 (상권업종) | S2 (업종명) |
| --- | --- | --- | --- |
| `CAFE` | 카페 | 중분류 비알코올 | 비알콜 음료점업 |
| `KOREAN` | 한식 (고깃집 포함) | 중분류 한식 | 한식 음식점업 |
| `CHINESE` | 중식 | 중분류 중식 | 중식 음식점업 |
| `JAPANESE` | 일식 | 중분류 일식 | 일식 음식점업 |
| `WESTERN` | 양식 | 중분류 서양식 | 서양식 음식점업 |
| `PUB` | 주점 | 중분류 주점 | 일반유흥 주점업 + 기타 주점업 (합산) |
| `FASTFOOD` | 패스트푸드 | 소분류 피자, 버거 | 피자 햄버거 샌드위치 및 유사 음식점업 |

S1은 상권업종 **중분류**로 가른다. 다만 `기타 간이` 중분류에는 치킨·김밥/만두/분식·빵/도넛처럼
S2에 대응 업종이 없는 소분류가 섞여 있어, `FASTFOOD`만 소분류(피자, 버거)로 좁혀 S2와 범위를 맞췄다.
S2는 고기요리를 따로 구분하지 않으므로 한식에 포함된다.
S3는 업종이 `음식점업` 하나뿐이라 동네 수치는 7개 업종 공통이며, 답변에는 "음식점업 전체 기준"으로 표기한다.

## 4. 걸러내기 규칙과 결과

버린 사실과 행 수를 `filter_log(rule, source, dropped_rows)` 테이블에 남긴다.

| 출처 | 규칙 | 버린 행 |
| --- | --- | --- |
| S1 | 행정동코드 없음 | 0 |
| S1 | 업종 소분류 없음 | 0 |
| S1 | 좌표 없음 | 0 |
| S1 | 좌표가 제주 범위 밖 (경도 126.0~127.1, 위도 33.0~34.1) | 0 |
| S1 | 음식 대분류이나 7개 업종 밖 — 뷰에서 제외 | 2,876 |
| S2 | 집계값 없음 | 0 |
| S2 | 이용금액 또는 건수가 0 이하 | 0 |
| S2 | 외식업 7개 업종 밖 — 뷰에서 제외 | 22,085 |
| S3 | 집계값 없음 | 0 |
| S3 | 이용건수 또는 소비금액이 0 이하 | 0 |
| S3 | 건당 금액 100만 원 초과 (입력 오류로 판단) · 전체 업종 기준 | 3,508 |
| S4 | 방문객 수 없음 (전부 2013~2017년) | 757 |
| S4 | 전체방문객수가 내국인+외국인과 불일치 — 재계산 | 2 |

### 4.1 판단 근거

**S3 극단값을 상하위 1%가 아니라 100만 원 기준으로 잘랐다.**
음식점업 건당 금액의 실제 분포는 1퍼센타일 3,123원, 중앙값 27,628원, 99퍼센타일 125,140원이다.
양 끝 모두 분식점과 고급 횟집으로 설명되는 정상값이라 1%를 자르면 실제 가게가 함께 사라진다.
명백한 입력 오류로 볼 수 있는 건당 100만 원 초과 28행(음식점업 기준)만 제외했다.

**S4 빈 값 757행은 전부 2013~2017년 구간이다.** 2018년 이후에는 하나도 없다.
지표는 최근 28일과 그 364일 전을 비교하므로 분석 구간에 영향이 없다.

**S4 전체방문객수는 원본을 쓰지 않는다.** 값이 모두 있는 날 중 2일이 내국인+외국인 합과 어긋나,
`v_arrivals.total_cnt`는 항상 두 값을 더해 다시 계산한다.

**7개 업종 밖 행은 버린 것이 아니라 뷰에서 제외된다.** 원본 테이블에는 남아 있으며 규모만 기록했다.

### 4.2 표본 부족 처리

S3는 계약 단위로 합친 뒤 **이용건수 100건 미만**이면 `low_sample = true`로 표시한다. 버리지 않는다.

| 범위 | 전체 칸 | 표본 부족 |
| --- | --- | --- |
| 음식점업 (분석 대상) | 10,365 | 657 (6.3%) — **전부 외국인 관광객** |
| 전체 업종 5종 | 48,558 | 8,024 (16.5%) |

도민과 내국인 관광객은 음식점업에서 해당 칸이 없다. 핵심 지표가 표본 부족으로 막히지 않는다.
지표 서비스는 최근 12개월에 표본 부족이 있으면 24개월로 기간을 넓히고, 답변에 그 사실을 밝힌다.

## 6. 데이터 한계

답변에 그대로 밝히는 한계다.

| 한계 | 내용 |
| --- | --- |
| **시간대 구분 없음** | 네 데이터 모두 월 또는 일 단위다. "저녁 장사가 나은가" 같은 질문에는 답하지 않는다 |
| **업력·생존기간 없음** | S1은 한 시점 스냅샷이라 개업일이 없다. "3년 버틴 가게"를 가릴 수 없다 |
| **개별 점포 매출 없음** | S2·S3 모두 집계값이고 점포 식별자가 없다. 특정 가게의 매출을 말할 수 없다 |
| **소득·소비 수준 없음** | 해당 데이터가 공개 범위에 없다 |
| **배달·홀 구분 없음** | 카드 데이터에 결제 채널 정보가 없다 |
| S2 지역 구분 없음 | 제주 전체 집계다. 동네 수치와 섞어 하나의 숫자로 말하지 않는다 |
| S3 업종 세분 없음 | `음식점업` 하나뿐이라 카페·주점 포함 여부가 확인되지 않았다. "음식점업 전체 기준"으로만 표기한다 |
| 기준 시점 불일치 | 점포 2025-09, 업종 카드 ~2025-06, 동네 소비 ~2026-09, 입도객 ~2026-11-16. 숫자마다 기준 시점을 함께 표기한다 |
| S1 등록 기준 | 상가 등록 정보라 실제 영업 여부와 다를 수 있다 |
| S3 추정치 | 카드사 점유율로 보정한 추정치이며 실제 소비 총액이 아니다 |

위 다섯 개 "없음" 항목은 평가 질문 30개 중 거절 문항 5개로 검증했고, 실제 평가에서 거절 정확도 100%를 기록했다.
