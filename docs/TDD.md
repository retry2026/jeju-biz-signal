# TDD — 테스트 먼저 쓰기

버전 1.0 · 2026-11-13

바이브 코딩은 AI가 그럴듯하지만 틀린 코드를 빠르게 만든다. 그래서 **사람이 정답을 먼저 정하고(테스트), AI가 그 테스트를 통과하는 코드를 쓰게 한다.** 이 문서는 역할별로 무엇을 먼저 테스트하는지 정한다.

## 1. 기본 흐름

1. **정답을 먼저 쓴다.** 손계산이나 문서(`API명세.md`, `metric-spec.md`)로 기대값을 정하고 테스트로 적는다.
2. **실패하는 것을 본다.** 구현 전에 테스트를 돌려 실패를 확인한다. 처음부터 통과하면 테스트가 잘못된 것이다.
3. **AI에게 구현을 맡긴다.** "이 테스트를 통과하게 구현해. 테스트는 고치지 마."
4. **통과를 확인하고 PR.** 테스트를 지우거나 기대값을 바꿔서 통과시키지 않는다.

AI에게 줄 때 쓰는 문장 예시:

> `AreaCustomerMetricTest`가 통과하도록 `AreaCustomerMetric.areaCustomers()`를 구현해. 테스트 파일은 수정하지 마. 뷰 `v_area_spend`만 조회하고, 비율은 퍼센트, 금액은 원 단위로 돌려줘. `API명세.md` 5장 record 그대로.

## 2. 역할별 테스트

### ① 데이터 — 값 대조 테스트

자동 테스트보다 **원본과 직접 비교**가 핵심이다.

| 무엇을 | 어떻게 | 언제 |
|---|---|---|
| 원본 테이블 행 수 | `SELECT count(*)`가 CSV 행 수(헤더 제외)와 같은지 | `01_raw.sql` 직후 |
| 매핑 누락 | `ref_area`에 43개 동이 모두 있고 `s3_name`이 비지 않았는지, `ref_industry`의 7개 업종이 S1·S2에서 1행 이상 나오는지 | `02_mapping.sql` 직후 |
| 걸러내기 | `filter_log`의 규칙별 버린 행 수가 0이 아니거나, 0이면 이유가 있는지 | `03_clean.sql` 직후 |
| 뷰 숫자 5개 | 예: 애월읍 2026-09 음식점업 도민 금액을 원본 CSV에서 엑셀로 직접 합산해 뷰 값과 비교 | `04_views.sql` 직후, `docs/data-check.md`에 기록 |
| 뷰 컬럼 | 컬럼 이름과 타입이 `API명세.md` 4장과 같은지 (`DESCRIBE v_area_spend`) | 합치기 전 |

자동화: `backend/src/test/.../config/DataLoaderTest`에서 앱을 띄워 뷰 4개가 존재하고 행이 1개 이상인지 확인.

### ② 지표 — 손계산 단위 테스트 (가장 중요)

숫자가 틀리면 에이전트 전체가 틀린다.

**방법:** `data/dummy/`의 작은 더미 데이터(뷰 모양, 각 20~50행)로 메모리 DuckDB를 만들고, 손으로 계산한 값과 비교한다.

| 테스트 | 더미 데이터 예 | 기대값 |
|---|---|---|
| 손님 구성 비중 | 한 동, 한 달: 도민 300만, 내국인 600만, 외국인 100만 | 30.0 / 60.0 / 10.0 |
| 건당 결제액 | 도민 300만 원 / 300건 | 10000 |
| 계절 변동폭 | 12개월 중 최대 200, 최소 100 | 2.0 |
| 전년 동월 대비 | 2026-09 110, 2025-09 100 | 10.0 |
| 표본 부족 | 12개월 중 일부 칸 `low_sample=true` | 해당 월 `null`, `meta.lowSample` 처리 |
| 동 점포 수와 평균 | 동 A 카페 4개, 동 B 2개 (2개 동) | storeCount 4, jejuAvg 3.0, densityRatio 1.33 |
| 반경 점포 수 | 좌표 기준 500m 안 3개, 밖 2개 | 3 |
| 업종 비중 (법인 제외) | 도민 50, 내국인 30, 외국인 20, 법인 100 | 50.0 / 30.0 / 20.0 |
| 계절 지수 | 월별 금액의 연평균 = 100 | 각 월 값 / 평균 × 100 |
| 입도객 전년 대비 | 올해 4주 합 1100, 작년 같은 4주 1000 | 10.0 |
| 없는 지역 | 존재하지 않는 동 코드 | 예외 또는 빈 결과 (정해서 테스트) |

**ChartAssembler 테스트:** 고정 record를 넣고 차트 7종 JSON의 `type`, `labels` 개수, `datasets[0].data` 값이 record와 같은지, 필요한 결과가 없는 차트 ID는 건너뛰는지.

### ③ 에이전트 — 계약 테스트와 평가

LLM 응답은 매번 달라서 단위 테스트로 정답을 고정하기 어렵다. 두 층으로 나눈다.

**층 1: LLM 없이 도는 코드 (단위 테스트)**

| 테스트 | 기대 |
|---|---|
| `InputGuard`: 지역이 비면 | `ASK_BACK`, `askFor=AREA`, LLM 호출 0번 |
| `LimitBuilder`: scope가 AREA와 JEJU인 결과 | 각 기준의 한계 문구 포함, "예측이 아님" 포함 |
| `EvidenceCollector`: 도구 2번 호출 | `evidence` 2개, 호출 순서 유지 |
| 응답 조립: 고정 `AgentReply` + 고정 도구 결과 | `ChatResponse`의 `charts`가 `chartIds` 순서대로, 숫자는 도구 결과와 같음 |
| `AgentReply`에 숫자 필드가 없음 | record 필드 검사 |

LLM 자리는 고정 응답을 돌려주는 가짜 `ChatModel`로 바꾼다.

**층 2: 실제 LLM으로 평가 (평가 하네스)**

평가 세트가 곧 에이전트의 인수 테스트다.

| 지표 | 계산 | PRD 목표 |
|---|---|---|
| 판단 정확도 | 응답 `type` = 기대 `type` | |
| 도구 선택 정확도 | 기대 도구가 모두 `evidence`에 있음 | 80% |
| 수치 정확도 | 정답 SQL 값이 본문에 허용 오차 안으로 있음 | 90% |
| 거절 정확도 | 거절 질문 5개 중 `REFUSE` | 100% |
| 근거 없는 숫자 비율 | 본문 숫자 중 도구 결과에 없는 숫자 | 0%에 가깝게 |

**프롬프트를 고칠 때마다 평가를 돌리고 결과를 남긴다.** 고치기 전보다 나빠지면 되돌린다.

### ④ 화면과 연동 — API 테스트와 화면 확인

| 테스트 | 방법 | 기대 |
|---|---|---|
| `POST /api/chat` 검증 | `@WebMvcTest` + `FakeChatAgent` | 필수 필드 없음 → 400 `INVALID_REQUEST`, `field` 표시 |
| 잘못된 코드값 | 같음 | `area`가 목록에 없으면 400 |
| LLM 오류 | `ChatAgent`가 `LLM_UNAVAILABLE`을 던지는 가짜 | 503 |
| `GET /api/meta` | 같음 | 지역 43개, 업종 7개 |
| 세션 정리 | `SessionStore` 단위 테스트 (시각 주입) | 30분 지난 세션 삭제 |
| 화면 타입 | `npm run build` (TypeScript 검사) | 에러 없음 |
| 화면 시나리오 | 예시 JSON 5개(A, B, C, 거절, 되묻기)로 화면을 띄워 캡처 | 응답 유형별 화면이 다름, 차트 표시 |
| 리셋 | 2분 기다리기 (개발 중엔 10초로 줄여 확인) | 처음 화면, 새 세션 |

## 4. 테스트 규칙

- 테스트는 지우거나 `@Disabled`로 끄지 않는다. 틀린 테스트는 사람이 판단해서 고친다.
- 테스트에 실제 LLM API를 쓰지 않는다 (평가 하네스만 예외). `./mvnw test`는 키 없이 통과해야 한다.
- 테스트는 원본 CSV(`data/raw`)가 아니라 더미(`data/dummy`)를 쓴다. 빠르고, 원본이 바뀌어도 깨지지 않는다.
- 기대값은 코드에서 계산하지 말고 숫자로 적는다 (`assertThat(r.residentShare()).isEqualTo(30.0)`).
